# cez mcp: a stdio MCP server so a Claude Code session can supervise cezar tasks (fork only)

- Date: 2026-10-06
- Category: feature
- Priority signal: medium — the user's daily workflow (supervising cezar tasks from an interactive Claude Code session) has no supported interface today
- Risk signal: medium — a new CLI subcommand and a new server runtime dependency, but no new HTTP route and no `server.ts` behavior change beyond the `POST /runs` schema de-dup
- Routing: Next: om-auto-write-spec "cez mcp: stdio MCP server so a Claude Code session can supervise cezar tasks (fork sheeerth/cezar only — PR against sheeerth/cezar main, never open-mercato) — brief: .ai/specs/briefs/2026-10-06-cez-mcp.md"

**Target repository: the fork `sheeerth/cezar`.** Every PR from this work is opened against `sheeerth/cezar` `main`, never against `open-mercato/cezar` (precedent: fork PR #5). The user explicitly chose not to engage upstream.

## Problem

The user works interactively in a Claude Code session in a terminal and wants that session to **supervise** cezar tasks: start a task, wait for it, read its status, the worker's latest output and the diff, send a corrective message, continue it, cancel it — a loop that repeats until the task reaches review. Sometimes the session fans out across several registered projects (one cockpit serves all of them) and collects the results.

Today such a session has two options: `curl` against `/api/v1` routes that have no endpoint reference (it guesses body shapes and what "finished" means), or read `.ai/cezar/runs.json`. `cez task` (`packages/cezar/src/dispatch/task-cli.ts`) does not fit: it only works **inside** a cezar task (it needs the engine-injected `CEZ_API_URL` / `CEZ_PROJECT_ID` / `CEZ_TASK_ID`) and its verbs are dispatch/report semantics tied to a parent run.

Upstream issue open-mercato/cezar#1109 proposes the same capability (with a contributor prototype and an open maintainer discussion); closed PR open-mercato/cezar#1263 was a different spec. This work does not depend on or touch either, but keeps names and shapes convergent with what #1109's thread settled, so a future sync conflicts as little as possible.

## Agreed direction

- A new CLI subcommand **`cez mcp`** speaking MCP over **stdio**, in `packages/cezar/src/mcp/`, registered like `task` / `automation` in `packages/cezar/src/index.ts` (early routing before `parseArgs` + lazy import). stdout carries JSON-RPC only.
- A **thin client of the already-running cockpit** over the existing `/api/v1` routes. No new HTTP routes. The only `server.ts` change is the `POST /runs` schema de-dup below.
- Dependency: **`@modelcontextprotocol/server` v2 (2.3.1)** — pulls `@modelcontextprotocol/core` (two packages total) plus `zod ^4.2`, which dedupes with the repo's zod 4.4; Node ≥ 20, ESM. It serves both protocol eras (2025-era clients and 2026-07-28). The commit adding it updates the runtime-dependency budget line in `CODE_REVIEW.md:52` and states the reason (Node ships no MCP implementation; the v1 `@modelcontextprotocol/sdk` has ~16 runtime deps). Note the line has already drifted (`dotenv`, `@clack/prompts`); correct it while there.
- Tool `inputSchema`s derive from `packages/contract` zod schemas — no second hand-written definition.

### Tools v1

Every tool sets `readOnlyHint` / `destructiveHint` explicitly; a unit test fails on any tool that does not. Every tool takes an optional `projectId`.

| Tool | Route(s) | Kind |
|---|---|---|
| `list_projects` | `GET /projects` | read |
| `list_workflows` | `GET /workflows` | read |
| `list_runs` | `GET /workspace/runs-index` | read |
| `get_run` | `GET /runs/:id` — a compact projection: status, current step, pending question, usage, branch | read |
| `get_run_messages` | first page of `GET /runs/:id/history` (newest events) — the worker's latest output | read |
| `get_diff` | `GET /runs/:id/diff` | read |
| `wait_for_runs(run_ids, timeout_s)` | polls `GET /runs/:id` (per project) | read |
| `start_run` | `POST /runs` | write |
| `send_run_message` | `POST /runs/:id/messages` | write |
| `continue_run` | `POST /runs/:id/continue` | write |
| `cancel_run` | `POST /runs/:id/cancel` | destructive |
| `finish_run` | `POST /runs/:id/finish` | destructive |

- **Start, then wait — never block for a whole run.** `start_run` returns the run id immediately. `wait_for_runs` checks once immediately, then polls every 2 s, and returns as soon as any listed run stops actively working — `waiting`, monitoring/parked, `review`, or any terminal status — or when `timeout_s` elapses (capped at ~45 s, under Codex's 60 s tool timeout), with the current state of every listed run either way. `run_ids` may span projects (each entry carries its `projectId`). One `AbortController` covers timeout and client cancellation.
- REST errors (`{ error }`, 404/409) come back as `isError: true` with the message, so the model can correct itself. Results are `structuredContent` plus the same JSON as text.
- `--read-only` registers only the read tools.

Rejected during the brainstorm:
- **MCP injected into cezar tasks instead of `cez task`** — `cez task` via Bash works on every backend; MCP would need per-backend config injection (Claude, Codex, OpenCode, Cursor…) for no new capability.
- **Contributing to / waiting for upstream #1109** — the user wants it in their fork now.
- **Build nothing (keep curl)** — no route reference; the agent guesses body shapes and completion semantics, and a supervision loop with fan-out is many calls. A cheaper "skill with curl examples" experiment was offered by the challenger and declined by the user: typed tools with hints and a server-side wait are the point, and #1109's prototype already exercised the shape.
- **Auto-starting the cockpit from `cez mcp`** — MCP must not manage a process; the user always runs `cez serve` in the background.
- **Port scanning / a runtime discovery file** — the cockpit's port is fixed (default 4321, `index.ts`), so a verified default suffices.
- **Equivalence test between the two `POST /runs` schemas** — preserves the duplicate; de-dup instead.

## Resolved unknowns

| Question | Answer (from the conversation) |
|----------|--------------------------------|
| Who is the client? | The user's own interactive Claude Code session (terminal). |
| Primary workflow? | Supervision loop (start → wait → read status/output/diff → message/continue → … → review); sometimes fan-out across several registered projects. |
| Transport? | stdio only. No HTTP `/api/v1/mcp`. |
| How is the cockpit found? | `--url` → `CEZ_API_URL` → `http://127.0.0.1:4321`, verified with `GET /api/v1/health`. (Corrected in the spec, A9: `cez serve` moves off 4321 when it is taken, so discovery probes 4321–4370.) |
| Cockpit not running? | `cez mcp` still starts and lists tools (so the client does not mark the server broken); each call returns `isError` "cockpit unavailable at <url> — run `cez serve`". No auto-start. |
| Dependency or hand-rolled JSON-RPC? | `@modelcontextprotocol/server` v2, justified in `CODE_REVIEW.md:52`. |
| Destructive tools in v1? | Yes: `cancel_run`, `finish_run`, with `destructiveHint: true`. |
| **Workers inheriting the MCP server** (challenger CRITICAL): a user-level Claude Code MCP registration is loaded by cezar's Claude-backend workers too, and `cez serve` puts `CEZ_API_URL` in their env (`index.ts:319`) — giving every task agent unbudgeted `start_run`/`cancel_run` that bypass dispatch's brakes (four children in flight, budget carved from the parent; AGENTS.md cites run 3f7eaf02, 4.3M tokens). | When `cez mcp` starts in a process whose env has `CEZ_TASK_ID`, it registers **only the read tools** (same filter as `--read-only`), regardless of flags. Pinned by a test. Agents inside tasks keep using `cez task` for dispatch. |
| Default project when `projectId` is omitted? | The registered project whose root contains the MCP server's cwd (matched via `GET /projects`); otherwise the cockpit's boot project (`default`). |
| How does the user run the fork's build? | `npm link` from the fork, so the global `cez` is the fork build (the global install is currently the npm release 0.14.0, which has no `mcp`). Client config: `{"command": "cez", "args": ["mcp"]}`. Document both in the fork's docs. |
| `POST /runs` schema duplication (`startRunSchema` in `server.ts` vs contract `createRunInputSchema`, field-identical today per #1109) | De-dup in this work: the route validates `createRunInputSchema`, `startRunSchema` is removed. `start_run`'s `inputSchema` derives from the same schema; a test posts what it advertises to the route. |
| Does reading the worker's latest output need `afterSeq` on `/history`? | No — the first `/history` page is the newest events (`event-history.ts`), which is what a supervisor reads. |
| Naming? | `cez mcp`; tool names as above, matching #1109's thread. |

## Non-goals

- Streamable HTTP transport (`/api/v1/mcp`) or any `CEZ_MCP` flag.
- PR create / push / merge, run deletion, worktree reclaim, config or agent-config writes, local-host routes (`open-in*`, `fs/browse`).
- `afterSeq` / forward cursor on `/history`.
- Dispatch/report tools, or any MCP injection into task worktrees.
- Upstreaming to `open-mercato/cezar` or coordinating with #1109.
- Auto-starting or managing the cockpit process.
